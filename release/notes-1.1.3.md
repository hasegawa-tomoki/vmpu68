VMPU68 1.1.3 — 16 MHz でのメイン RAM 書込み欠けの修正(Raspberry Pi 4 カーネル 1.1.3 / FPGA 1.0.1)

## 修正・改善
- Pi からメイン RAM への書込みがまれに欠ける問題を直しました(FPGA 1.0.1)。原因は二つありました。
  1. 書込みデータを出してから AS までの余裕(wr_setup)が、既定の 4 クロック型バスサイクルでは効いていなかった
     (1.1.2 まで。16 MHz で約 1 万ワードに 1 つ、ビットが落ちる形)。
  2. 書込みストローブの解除が本物の 68000 より半クロック早く、主記憶の 4 ビット幅 DRAM のうち 1 個だけ書込みが成立しない
     ことがあった(上位 4 ビットか下位 12 ビットの片方が古い内容のまま残る形。V1.0 基板では 1.1.2 で約 1000 ワードに 1 つ、
     修正 1 だけでは約 30 万ワードに 1 つ)。書込みの終端を 68000 と同じ長さにしました。
  3. 電源を入れた直後の数分間だけ、16 MHz で Pi からメイン RAM への書込みが 100 ワードに 1 つほど欠けていました(温まると
     100 万ワードに 1 つ以下)。FPGA はバスクロックの 61/16 倍の内部クロックでバスクロックをサンプリングして動くため、AS や DS の
     出る位置がサイクルごとに 16 ns の幅で揺れ、その一部が本体のサンプリング点に掛かっていました。掛かる割合が温度で変わるので
     投入直後だけ目立ちます。本物の 68000 はこの位置に出さないので起きません。4 クロック型(16 MHz 級)ではバス出力を
     内部クロック 1 個(約 16 ns)遅らせて出すようにしました(FPGA 1.0.1)。10 MHz 級(5 クロック型)は従来どおりです。
     遅らせる量(内部クロック 0〜3 個)は FPGA の設定レジスタで Pi 側から選び、カーネルが基板とクロックに応じて決めます
     (vmpu68-bus.json の out_delay で上書き可、/api/status の out_delay で確認)。
  X68000 側から DMAC で読み戻して照合する検査(WRTEST、dmaw)で、V1.0 / V2.0.1 基板とも欠け 0 を確認しています。
  投入直後の確認は V2.1 相当の基板で行いました(電源 OFF 10 分 → ON の直後から 12 分間、欠け 0)。
- 10 MHz のとき、Pi から VRAM への書込みと VRAM の読み出しが化けることがある問題(画面に点状のゴミ、FPGA のビットストリームの
  配置次第で出たり出なかったりする)への対処として、10 MHz 級ではバスサイクルを 5 クロック型(読みが 1 バスクロック長い)に
  しました。16 MHz 級は従来どおり 4 クロック型です。`vmpu68-bus.json` の `slow`("auto" / true / false)で固定できます。
  通常は "auto" のままで構いません。
- 起動時の書込み検査(wr_setup の自動探査)を強化しました。メイン RAM の 1 MB 以降 128 KB を使い、各設定で 131072
  ワードを両方向(0→1、1→0)で確かめます(1.1.2 の 16384 ワードでは上の欠けを 19% の確率で見逃していました)。
  各設定の欠け数は起動ログと `/api/status` の `probe_lost` に出ます。欠けのない設定が無いときは最も少ない設定を使います。
- お試し更新(try)で FPGA を書き換えるとき、それまでのビットストリームを SD カードに退避し(`fpga-prev.bin`)、
  お試し起動が失敗したときに戻すようにしました。昇格の条件も「20 秒生存」から「20 秒生存 + 書込み検査が健全 +
  エミュレータが動いている」に変えました。120 秒たっても満たさないときは元に戻して安定側で再起動します。
  (1.1.2 から 1.1.3 への更新では戻す側の仕組みがまだ無いので、FPGA は戻りません。)
  また、お試しカーネルが一度も起動しないまま電源を切った場合に、次の安定起動が自分をお試しと誤認して壊れたカーネルを
  昇格させる可能性があった問題を直しました(お試しカーネルのビルド日時を記録して照合します)。
- DMAC のバースト転送(IOCS _DMAMOVE など)の直後に CPU がその領域を読むと、ごくまれに転送前の内容が見えることがある問題を
  直しました。転送中にスヌープ(DMAC の書込みをシャドウ RAM に反映する仕組み)の記録があふれ、修復の再読込が CPU の読みに
  間に合わないことがあったためで、CPU が I/O レジスタを読む・割込みを受けるたびに記録を全部反映してから先へ進むようにしました。
  副次効果として、転送中のあふれ自体も起きなくなっています。
- Pi コンソールに `fill` / `chk`(WRTEST と同じパターンの書込み・照合)、`dmaw`(Pi が書いた領域を DMAC で複写し、実 RAM と
  シャドウ RAM を突き合わせて化けの種類を分ける診断)を追加しました。
- `/api/status` に `bus_slow`、`probe_ok`、`probe_lost`、`ab`(A/B ブートの状態)、`temp_c`(Raspberry Pi の SoC 温度)、
  `throttled`(Raspberry Pi ファームウェアの電源監視フラグ。bit0 = いま電圧低下、bit16 = 起動後に電圧低下があった)を追加しました。
  コンソールの `cpu` コマンドにも同じフラグが出ます。電源の弱い環境の切り分けに使えます。
- 書込みデータの保持を、ストローブ解除後 半バスクロック(68000 と同じ)にしました。V2.1 基板向けのピン(DTACK 駆動 = OFF、
  PSRAM CE# = 無効)を定数で駆動するようにしました(V1.0 〜 V2.0.1 では未接続のピンです)。

基板 V1.0 〜 V2.0.1 共通です。V2.1 基板(PSRAM 付き)の対応は別の系統で進めています。
